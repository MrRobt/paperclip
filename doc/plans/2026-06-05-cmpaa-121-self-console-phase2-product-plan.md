# CMPAA-121 自家控制台二阶段提效需求与验收口径

> 面向 Paperclip 自家二开：把真实使用暴露的调度、验收、噪声、恢复链和团队可观测问题，沉淀为可实施的产品方案。

## 1. 目标

二阶段目标不是增加更多自动化噪声，而是让一个小型智能体公司稳定形成“派活 → 执行 → 复审 → 验收 → 纠偏”的闭环。

成功标准：

1. 同一时间每个成员只承接一个最高优先级任务。
2. 核心小队可被一键启用，非核心成员默认不参与调度。
3. 任务二十分钟内没有有效六件套时，系统主动建议缩小任务或拆子任务。
4. 三闸门验收把“真实产出”和“运行噪声/评论噪声/恢复链打转”区分开。
5. 团队健康页能直接看见成员、任务、运行、证据、卡点和下一步裁决。
6. 所有写入仍走 Paperclip 接口，不直接改数据库。

## 2. 设计原则

- 控制台优先：Paperclip 是控制平面，不把原始终端日志当主界面。
- 最小可验证：先做规则、指标和页面闭环，再做复杂自动裁决。
- 人可裁决：自动化只能建议缩小、暂停、转派；删除远端修改、关闭长期链路等高风险动作需要人确认。
- 有效产出优先：文件、提交、测试、截图、可访问链接、验收评论优先于“我正在做”。
- 噪声可折叠：重复恢复、重复醒来、空泛评论必须聚合，不刷屏。

## 3. 角色与权限

| 角色 | 职责 | 主要动作 | 禁止动作 |
|---|---|---|---|
| 总控/老板 | 定方向、裁决长期阻塞、确认高风险变更 | 启停核心小队、确认三闸门、批准强制转派 | 直接改库强修复 |
| PM | 拆需求、维护验收口径、判断噪声 | 创建/拆分任务、补充验收清单、发起复审 | 以运行日志代替验收 |
| 工程师 | 执行单一高优任务 | 接单、提交六件套、补证据 | 同时抢多个高优任务 |
| 复审员 | 独立验收 | 读差异、跑命令、标记通过/驳回 | 只看评论不看产出 |
| 系统守护 | 监控运行状态 | 标记超时、聚合噪声、建议缩小任务 | 自动删除任务或直接改业务数据 |

## 4. 核心小队模式

### 4.1 产品需求

新增“核心小队模式”开关，默认只让核心成员进入自动唤醒和高优调度池。

字段建议：

- `agents.runtime_config.teamMode.enabled`: 是否纳入小队模式。
- `agents.runtime_config.teamMode.role`: `builder | reviewer | pm | operator`。
- `agents.runtime_config.teamMode.maxActiveHighPriorityIssues`: 默认 1。
- `agents.runtime_config.teamMode.autoWakeEnabled`: 是否自动唤醒。
- `agents.runtime_config.teamMode.pauseReason`: 被暂停调度原因。

### 4.2 页面

入口：团队页或公司设置页新增“核心小队”标签。

页面模块：

1. 小队成员列表：姓名、角色、当前任务、最后真实产出时间、是否允许自动唤醒。
2. 非核心成员列表：显示暂停原因和“临时启用一次”按钮。
3. 调度规则卡片：一人一高优、二十分钟六件套、三执行一复审、恢复链裁决。
4. 风险提示：启用自动唤醒前展示今日运行数、失败数和预算消耗。

### 4.3 接口

- `GET /api/companies/:companyId/team-mode`：读取小队配置和成员状态。
- `PATCH /api/companies/:companyId/team-mode`：更新全局小队规则。
- `PATCH /api/agents/:agentId/team-mode`：更新单个成员调度资格。
- `POST /api/companies/:companyId/team-mode/wakeup`：只唤醒符合规则的成员。

验收：

- 非核心成员不会被批量唤醒。
- 核心成员已有未完成高优任务时，不再分配新的高优任务。
- 页面能看到为什么某个成员被跳过。

## 5. 三执行一复审

### 5.1 产品需求

同一批功能任务必须至少形成“三执行一复审”结构：三个执行切片可以并行推进，一个独立复审任务负责验收产出。

适用场景：

- 涉及前后端联调。
- 涉及接口、安全、状态机或恢复链。
- 涉及多个成员提交产出。

### 5.2 任务模型补充

在 issue 上增加或派生以下元信息：

- `executionPolicy.reviewRequired`: 是否必须复审。
- `executionPolicy.reviewGate`: `none | required | passed | failed`。
- `executionPolicy.batchId`: 同一批任务标识。
- `executionPolicy.role`: `execution | review`。

### 5.3 状态流

```text
backlog → todo → in_progress → submitted_for_review → review_in_progress → done
                                      ↘ failed_needs_rework → todo
```

规则：

1. 执行任务提交六件套后进入 `submitted_for_review`。
2. 复审员必须读取产物和验证命令，不能只根据评论通过。
3. 复审失败时必须写明失败证据和最小返工项。
4. 复审通过后才允许父任务完成。

## 6. 一人一个高优任务

### 6.1 产品规则

每个成员同时最多一个 `critical/high` 且非完成任务。

冲突处理：

1. 已有运行中高优任务：新任务保持 `backlog` 或提示 PM 转派。
2. 已有待办高优任务但二十分钟无六件套：触发缩小任务建议，不直接派新任务。
3. 多个同优先级任务：按父目标优先级、创建时间、阻塞其他任务数量排序。

### 6.2 接口校验

在以下写入点做校验：

- 分配负责人。
- 状态改为 `todo/in_progress`。
- 批量唤醒。
- 自动恢复链创建任务。

返回错误需包含：成员当前任务、冲突任务标识、建议动作。

## 7. 二十分钟无六件套即缩小任务

### 7.1 六件套定义

有效完成评论必须包含：

1. 改动摘要。
2. 分支。
3. 提交号或明确说明“文档-only 未提交/无需提交”的原因。
4. 验证命令。
5. 验证结果。
6. 下游复验口径。

### 7.2 有效产出判定

计入有效产出的证据：

- 新增或修改的文件路径。
- 提交号。
- 通过的验证命令输出。
- 页面截图或可访问链接。
- 明确的阻塞项，且包含已尝试方案和下一步最小方案。

不计入有效产出的噪声：

- “正在处理”“继续推进”“已恢复”。
- 重复贴旧日志。
- 无文件、无命令、无截图、无下一步的泛泛评论。
- 恢复链反复创建但没有改变故障状态。

### 7.3 缩小任务动作

二十分钟没有有效六件套时，页面和系统守护给出三选一：

1. 缩小范围：保留当前任务，只把验收目标压缩成一个最小可验证点。
2. 拆子任务：把强依赖拆出，当前任务转为父任务。
3. 人工裁决：长期卡住或涉及高风险删除时提醒总控接管。

自动动作只允许写评论和创建建议，不允许自动关闭任务。

## 8. 三闸门验收

### 8.1 闸门一：产物闸门

必须至少满足一项：

- 有仓库文件变更。
- 有提交号。
- 有文档产物路径。
- 有接口返回样例、截图、链接或测试报告。

失败示例：只有“我完成了”的评论。

### 8.2 闸门二：验证闸门

必须包含可复跑命令和结果：

- 文档类：`git diff --check -- <文档路径>`。
- 后端类：目标单测、类型检查、最小服务健康检查。
- 前端类：目标单测、构建或真实浏览器验证。
- 接口类：`curl` 样例和响应摘要。

失败示例：只写“未验证”。

### 8.3 闸门三：复验闸门

必须写清下游如何复验：

- 打开什么页面。
- 调哪个接口。
- 看哪个文件。
- 预期看到什么。
- 失败时回退或驳回标准。

失败示例：没有下游复验路径。

## 9. 噪声治理

### 9.1 噪声分类

| 类型 | 判定 | 页面处理 | 系统动作 |
|---|---|---|---|
| 运行噪声 | 心跳启动/恢复但无产物 | 折叠到运行时间线 | 不计入有效进度 |
| 评论噪声 | 空泛进展、重复旧证据 | 标记低价值 | 提醒补六件套 |
| 恢复链噪声 | 同源故障重复创建恢复任务 | 合并成一个恢复组 | 提醒裁决 |
| 验收噪声 | 未跑命令直接通过 | 标记验收不可信 | 要求复审员补证据 |

### 9.2 页面表现

- issue 详情页新增“证据质量”卡片。
- 评论流默认折叠低价值重复评论。
- 恢复链显示为“同源恢复组”，只突出最新有效变化。
- 列表页用徽标显示：`有六件套`、`待复审`、`噪声偏高`、`需裁决`。

## 10. 恢复链裁决

### 10.1 触发条件

满足任一条件即进入“需裁决”：

- 同一源问题 2 次以上恢复仍失败。
- 恢复任务没有新证据，只重复唤醒。
- 恢复动作可能删除远端修改、重置分支或强改状态。
- 原成员连续超时且没有六件套。

### 10.2 裁决动作

- 暂停原恢复链。
- 指派总控或复审员接管。
- 要求先复现运行态，再决定修复、转派或关闭。
- 高风险动作必须展示影响范围并等待人工确认。

## 11. 团队健康页

### 11.1 页面目标

让总控在一个页面回答五个问题：

1. 谁正在真正干活。
2. 谁只是在产生日志或空评论。
3. 哪些任务已经有可验收产物。
4. 哪些恢复链在打转。
5. 下一步该唤醒、缩小、复审、接管还是暂停。

### 11.2 页面区域

1. 总览指标：开放高优任务数、有效产出数、噪声评论数、待复审数、需裁决恢复链数。
2. 成员矩阵：成员、角色、当前任务、最后心跳、最后有效产出、健康状态。
3. 任务泳道：高优待办、运行中、待复审、返工、需裁决。
4. 恢复链面板：按源问题聚合，显示失败次数和最新证据。
5. 操作区：唤醒核心小队、缩小任务、发起复审、暂停噪声链。

### 11.3 接口

- `GET /api/companies/:companyId/health/summary`。
- `GET /api/companies/:companyId/health/agents`。
- `GET /api/companies/:companyId/health/issues`。
- `GET /api/companies/:companyId/health/recovery-groups`。

接口返回应包含证据来源时间戳，避免把旧状态当新状态。

## 12. 验收指标

| 指标 | 目标 | 计算口径 |
|---|---:|---|
| 高优任务并发冲突 | 0 | 每个成员未完成 critical/high 任务数不超过 1 |
| 六件套覆盖率 | ≥ 90% | 完成评论中满足六字段的比例 |
| 二十分钟缩小提醒命中率 | 100% | 超时无有效产出的任务均有提醒或裁决 |
| 噪声折叠率 | ≥ 80% | 重复运行/评论被折叠的数量占比 |
| 复审有效率 | ≥ 90% | 复审评论包含验证命令和结果的比例 |
| 恢复链打转可见性 | 100% | 同源二次失败均进入恢复组并显示需裁决 |

## 13. 实施切片

### 第一阶段：规则和文档落地

- 完成本文档。
- 明确六件套、噪声、三闸门、恢复链裁决的判定口径。
- 在团队内按此口径执行人工验收。

验收：本文档存在于 `doc/plans/`，并通过 `git diff --check`。

### 第二阶段：后端规则最小实现

- 增加六件套解析服务。
- 增加一人一高优校验。
- 增加恢复链同源聚合查询。
- 增加健康页汇总接口。

验收：服务单测覆盖正反例；接口可用 `curl` 返回摘要。

### 第三阶段：前端健康页和任务详情证据卡

- 新增团队健康页。
- issue 详情页新增证据质量卡。
- 评论流折叠噪声。
- 任务列表展示待复审/噪声/需裁决徽标。

验收：前端单测通过，真实浏览器可看到核心指标和折叠效果。

### 第四阶段：调度联动

- 批量唤醒只唤醒核心小队。
- 自动分配遵守一人一高优。
- 二十分钟无六件套写入缩小任务建议。
- 复审未过不允许父任务完成。

验收：构造多个任务和成员，验证调度跳过、提醒、复审状态流均正确。

## 14. 风险与待决策

| 风险 | 影响 | 建议 |
|---|---|---|
| 六件套靠文本解析误判 | 误把有效工作当噪声 | 先用显式模板和宽松匹配，后续再做结构化字段 |
| 规则太硬阻塞交付 | 成员无法接急单 | 允许总控手动覆盖，但必须记录原因 |
| 健康页指标读取旧数据 | 误判成员状态 | 所有指标显示来源和时间戳 |
| 恢复链自动裁决过度 | 误停真正修复 | 系统只建议，最终由人确认 |
| 新状态影响旧流程 | 回归风险 | 先用派生字段/服务计算，不立即改核心枚举 |

待决策：

1. 是否把 `submitted_for_review` 做成正式 issue 状态，还是先用 `executionPolicy.reviewGate` 派生展示。
2. 六件套是否需要结构化评论模板接口。
3. 核心小队配置放在 agent runtime_config，还是新增独立 team profile 表。
4. 二十分钟超时是否按任务 startedAt 计算，还是按最后有效产出时间计算；建议用后者。

## 15. 下游复验口径

复验人按以下顺序检查：

1. 打开本文档路径：`doc/plans/2026-06-05-cmpaa-121-self-console-phase2-product-plan.md`。
2. 核对是否覆盖角色、页面、接口、状态机和验收指标。
3. 运行 `git diff --check -- doc/plans/2026-06-05-cmpaa-121-self-console-phase2-product-plan.md`。
4. 对照 CMPAA-121 描述，确认核心小队、三执行一复审、一人一高优、二十分钟六件套、三闸门、噪声治理、恢复链裁决、团队健康页均已覆盖。
