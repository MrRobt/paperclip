# 纸夹智能体交付系统完整需求

状态：进行中

## 一、总目标

构建一个面向多智能体团队的实时交付系统，覆盖“任务派发、执行观测、阻塞治理、评论可靠投递、证据验收、恢复动作、模型通道自愈、管理端控制台、审计追踪”的完整闭环。

## 二、用户故事

### 需求一：主控能一眼判断团队是否阻塞

作为主控，我要在一个页面看到所有非终态事项的健康状态，包含：

- 是否有活跃运行。
- 是否有排队唤醒。
- 是否被强阻塞、弱阻塞或提示阻塞影响。
- 是否缺少工作产物、验证命令、证据路径或提交号。
- 是否存在评论失败、唤醒跳过、适配器异常、模型异常。
- 下一步动作是谁负责，是智能体、系统、主控还是人工。

验收标准：

- 提供公司级诊断列表接口。
- 提供单事项诊断接口。
- 输出结构稳定，可被前端直接渲染。
- 对每条异常给出原因、严重级别、下一步动作和负责人。

### 需求二：评论失败不能丢

作为智能体或主控，我希望评论写入失败时不会静默丢失，而是生成草稿，后续可以重放。

验收标准：

- 新增评论草稿持久化表。
- 所有评论写入失败路径都能保存草稿。
- 支持查询草稿、单条重放、批量重放。
- 重放成功后关联真实评论编号。
- 重放失败记录失败原因和尝试次数。

### 需求三：阻塞可分级、可降级、可旁路补证据

作为主控，我要区分真实不可继续的阻塞和只是风险提示的阻塞。

验收标准：

- 支持强阻塞、弱阻塞、提示阻塞。
- 强阻塞禁止继续执行推进，但允许补评论、补证据、补诊断、创建恢复动作。
- 弱阻塞允许继续补证据、补接口验证、补复审材料。
- 提示阻塞只展示风险，不阻止执行。
- 阻塞升级和降级要写活动日志。

### 需求四：恢复动作形成闭环

作为主控，我要系统在静默、运行丢失、唤醒跳过、模型失败时生成可执行恢复动作，而不是只显示“卡住”。

验收标准：

- 复用并扩展现有恢复动作表。
- 诊断聚合器能关联恢复动作状态。
- 支持一键恢复、批量恢复、重新唤醒、转人工、生成独立修复事项。
- 每个恢复动作有来源、原因、负责人、截止时间、结果。

### 需求五：模型和适配器异常可自愈

作为运营者，我要系统识别模型通道、适配器、命令行进程、接口超时等异常，并自动给出重试或降级策略。

验收标准：

- 新增模型健康服务。
- 按适配器、模型、智能体聚合失败率、超时率、最近错误。
- 支持策略：原模型重试、同适配器降级模型、切换备用适配器、暂停并转人工。
- 策略执行必须可审计，不能绕过预算或审批。

### 需求六：完成证据强绑定

作为主控，我不接受智能体只说“完成了”，必须看到可复核证据。

验收标准：

- 完成事项前检查工作产物、验证命令、验证结果、证据路径、提交号或明确无提交原因。
- 证据不足时不能自动完成，只能进入待复审或补证据。
- 前端显示证据完整度评分。
- 服务端完成接口统一走证据闸门。

### 需求七：实时交付控制台

作为主控，我要在前端实时看到团队交付状态，并能执行控制动作。

验收标准：

- 新增“交付控制台”页面。
- 展示健康总览、风险队列、草稿队列、恢复动作队列、模型健康、事项证据完整度。
- 支持筛选公司、项目、智能体、状态、严重级别。
- 支持一键唤醒、重放评论、执行恢复、打开事项、查看日志。
- 页面失败必须明确提示，不得静默失败。

### 需求八：实时性与可观测

作为主控，我要状态接近实时更新，而不是只能手动刷新。

验收标准：

- 优先复用现有接口轮询模式；如已有事件通道则接入。
- 页面有刷新时间和数据时效提示。
- 后台任务写结构化日志和活动日志。
- 诊断快照可追踪变化，不只展示当前值。

## 三、暂不做事项

- 不做云级多租户权限体系重构。
- 不做公开市场或插件市场。
- 不做真实外部触达自动审批绕过。
- 不替换现有适配器架构。
- 不重写纸夹核心事项模型。

## 四、质量要求

- 服务端新增服务必须有单元测试。
- 新接口必须有契约测试或路由测试。
- 数据库改动必须生成迁移并同步导出。
- 前端核心页面必须至少有组件级或端到端冒烟验证。
- 最终收口前运行：`pnpm -r typecheck`、`pnpm test:run`、`pnpm build`。

## 五、需求追踪编号

- 交付系统一：诊断聚合。
- 交付系统二：评论草稿可靠投递。
- 交付系统三：阻塞分级。
- 交付系统四：恢复动作闭环。
- 交付系统五：模型通道自愈。
- 交付系统六：完成证据强绑定。
- 交付系统七：前端实时控制台。
- 交付系统八：审计与观测。
